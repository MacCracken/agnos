# 1.56.51 P-1 audit sweep — the backlog that did not land

**Opened** 2026-08-28, at the close of the 1.56.51 audit/hardening sweep.

## ⭐⭐ STATUS — 1.56.52 (2026-08-29): BOTH P0s CLOSED

**P0: 2 of 2 closed.** `elf.cyr:312` closed at 1.56.51 by the architecture change; `syscall.cyr:1895`
(`#92` op 0x0C TOCTOU) closed at 1.56.52 by stage-and-revalidate. The `#92` battery grew 167 → 171 with
two post-validation mutation cases and a control, and the pair is mutation-tested.

**P1: 21 of 26** (20 fully + 1 partial). **P2: 29 of 29 — CLOSED.**

⛔ **One P1 turned out to be sitting on a P0 that is in NO backlog** — `proc.cyr:1781` (the high arena is unreachable through the syscall ABI) could not be fixed as filed, because `is_user_range` was a bounds check and the low window is full of supervisor identity mappings of kernel memory. See that item's RESOLUTION block. This is the second time in this backlog that the severity label was wrong in the dangerous direction.

⛔ **A P2 turned out to be a P0, and a bug NOBODY HAD FILED turned out to be a privilege escalation.**
Re-triaging the P2 list against the code (rather than trusting its label) moved four items up:
- `proc.cyr:1830` (filed P2) is a **P0**: `sys_munmap` had no ingress cap on `length`, so `addr + len`
  wrapped negative past a signed ceiling test, `pd_idx` cycled into the kernel identity window, and —
  because the free site checked only the present bit, never the user bit — `pmm_free_2mb` marked
  physical 2-256 MB **free while live**. Two integers through syscall 28.
- `elf.cyr:357` and `proc.cyr:1788` are **P1** ring-3 memory exhaustion, not cleanup.
- `kfmt.cyr:40` is a real out-of-bounds stack write across all 30 `fmt_hex_buf` call sites, and it is
  **interlocked** with `kfmt.cyr:28`: fixing the negative-render bug is what makes `len == 16` common.
- ⭐ **`gdt.cyr:82` was not in this backlog at all.** The TSS I/O-map base was written to offset 100
  (reserved) instead of 102, leaving the real base at 0 — below the TSS limit — so the CPU believed an
  I/O permission bitmap started at `TSS+0`, where zero bits mean ALLOWED. Ports `0x000-0x33F` were open
  to ring 3, including `out 0x64, 0xFE` (CPU reset). Ports `>= 0x340` correctly `#GP`, so COM1 still
  faulted: a silent PARTIAL failure, which is why twelve auditors missed it.

⚠ **Findings whose severity the audit OVERSTATED, corrected here:** `elf.cyr:484`'s init-stack overrun
spills into the child's **own** stack page (the loader writes through `stack_kva`), so it corrupts that
child's argv — it is not a kernel-memory escape.

⚠ **Two of the audit's own suggested fixes were wrong and were not taken as written:** the `blk` RW-arm
reorder is an ABI break (measured, reverted at 1.56.51), and the init-stack guard it proposed
(`argc + envc + 4 > slots`) is **off by one**, too permissive by exactly one slot.

## What this is, and what it is not

The 1.56.51 sweep ran 12 subsystem auditors over the kernel and adversarially verified every finding
with an independent refuter whose default answer was REFUTED. 101 raw findings; 79 survived; 13 were
refuted outright. This file is **what survived and was not fixed** — the fixed ones are in
[`CHANGELOG.md`](../../../CHANGELOG.md) under 1.56.51 and are not repeated here.

⚠ **These are LEADS, not verdicts.** Each was traced by one auditor and challenged by one refuter,
and neither ran the kernel. Confirm against the code before acting — the sweep produced real false
positives, and their shape is instructive: **one auditor read `var x[N]` as N bytes when it is N u64
slots (N*8 bytes)** and generated a whole cluster of phantom "64-byte buffer, 512-byte write"
overflows in `user/shell.cyr` and `usb/msc.cyr`. Every one was wrong. Those are excluded here.

⛔ **Nine verifiers were lost to a spend limit** (all in the klib/cross-arch area). Findings from that
area therefore carry a finder's claim with no refuter behind them — treat them as the weakest.

## How to work this list

1. Read the site. Trace to the entry point — most suspicious lines in this kernel are guarded
   somewhere the finder did not look.
2. Prove the failure with concrete 64-bit values before writing a fix. Several 1.56.51 fixes were
   only correct because the arithmetic was worked out first.
3. Boot after each change, and **check the kernel banner** — a QEMU run that never left OVMF reads as
   a wall of assertion failures. See `state.md`'s note on `qemu_dwell_kernel`.


## P0 — memory-safety or privilege, reachable from ring 3 or untrusted media — 2 item(s) · 1 FIXED

### ✅ FIXED 1.56.51 — `kernel/core/elf.cyr:312` — ELF PT_LOAD may be mapped anywhere in the per-process kernel-identity PD window (PD[2..127]), shadowing the kernel's own page tables and heap under the child's CR3

**Mechanism.** Both loaders bound a PT_LOAD only by `p_vaddr >= 0x400000` (elf.cyr:102/:284/:308) and `p_vaddr + p_memsz <= 0x10000000` (elf.cyr:74/:109/:286/:312). That accepted span, [0x400000, 0x10000000) = 4 MB .. 256 MB, is exactly PD indices 2..127 of the per-process page directory. proc_create_address_space builds those very slots as the KERNEL IDENTITY window: PD[0..127] are copied from the boot PD and PD[8..127] are re-asserted as `(hi * 0x200000) | 0x83` (proc.cyr:684-699). The loader then calls proc_map_page / proc_map_page_nx (elf.cyr:129-130, :340-341), whose only index math is `pd_idx = (virt >> 21) & 0x1FF` (proc.cyr:1094, :1122) — so a segment at p_vaddr = 0xC00000 OVERWRITES PD[6] with `user_phys | 0x87`, destroying the identity mapping for physical 12-14 MB in that process's address space.

That matters because the kernel dereferences physical addresses AS VIRTUAL ADDRESSES while running under the caller's CR3. pmm.cyr:22-28 states the premise itself: "A syscall (e.g. mmap) runs under the CALLER's CR3". Every one of proc_map_page (proc.cyr:1089-1103), proc_map_page_nx (:1118-1130), proc_map_page_hi (:1517-1529), proc_unmap_page (:1667-1687), proc_get_user_cr3 (:998-1002) and sys_munmap (:1831-1834) begins with `load64(cr3)` where `cr3` is a raw physical page number. Every kmalloc'd kernel object is likewise a raw pmm_alloc address (heap.cyr:50, :69, :113).

And the pmm 4 KB pool is *entirely contained* in the attacker-reachable window: pmm_alloc scans `for (var i = pmm_alloc_top; i >= 1024; i = i - 1)` (pmm.cyr:560) with pmm_alloc_top clamped to 65535 (pmm.cyr:224), i.e. phys in [0x400000, 0xFFFF000] — a strict subset of [0x400000, 0x10000000). So the process's own PML4/PDPT/PD pages and the whole kernel heap always live at identity VAs a PT_LOAD can shadow.

pmm.cyr:317-321 asserts the opposite as a load-bearing invariant — "the ONLY per-proc PDE override inside the kernel-identity range PD[0..127] (0-256 MB) is PD[2] (ring-3 code @ 0x400000)" — and pmm.cyr:324-325 admits "The kernel heap (~PD[127]) + .bss are below PD[2]-aliasing risk only by luck of placement". proc.cyr:206-215 documents the *same* class already having fired once ("a large binary ... clobbered PD[7] in its own CR3"), but it was closed only for the TSS RSP0 stack by moving that one consumer to the direct map. elf.cyr:276-283 closed it only for PD[1]. The page tables and the heap were never moved off identity VAs.

**Failure trace.** 1. Attacker writes /tmp/x, an ELF64 with e_entry 0x400000 and two PT_LOADs: (a) the real RX code at 0x400000, (b) a PF_R|PF_W segment with p_vaddr = 0xC00000, p_memsz = 0x200000, p_filesz = 0x200000 carrying a crafted 2 MB payload. Both pass every check at elf.cyr:264-288 and :303-312.
2. Ring 3 calls execwait#37 / spawn_path#43 on it. elf_load_from_file calls proc_create_address_space (elf.cyr:290); with pmm_alloc_top = 4095 (plain multiboot boot: boot_info_ptr == 0 so pmm_extend_to_memmap returns at pmm.cyr:175) the top-down scan skips reserved region 7 (pages 3584-4095, pmm.cyr:501) and returns pages 3583/3582/3581 = phys 0xDFF000 / 0xDFE000 / 0xDFD000 as new_pml4 / new_pdpt / new_pd. All three sit in PD[6] (0xC00000-0xE00000).
3. The PT_LOAD loop (elf.cyr:325-362) reaches segment (b) and calls proc_map_page_nx(new_cr3, 0xC00000, phys_user). proc.cyr:1122 computes pd_idx = 6 and proc.cyr:1123 stores `phys_user | 0x8000000000000087` into new_pd[6]. The child's identity mapping of 12-14 MB is gone; VA 0xDFF000 now resolves to phys_user + 0x1FF000, a page ring 3 can write.
4. The child runs and issues mmap#27. sys_mmap (proc.cyr:1747) fetches cr3 = 0xDFF000 and calls proc_map_page_nx(0xDFF000, base, phys) at proc.cyr:1776, running under the child's own CR3.
5. proc.cyr:1118 executes `load64(0xDFF000)` -> reads the attacker's payload, not the PML4. The attacker set that qword to 0x00C00000, so pdpt_addr = 0xC00000 (its own page). proc.cyr:1120 reads pdpte from there = attacker value, so pd_addr = 0x1000 (the kernel boot PML4).
6. proc.cyr:1123 executes `store64(0x1000 + pd_idx * 8, phys | 0x8000000000000087)` — a 64-bit write of a semi-controlled value to a kernel-chosen physical address. proc.cyr:1124 then reads `load64(pd_addr + 511*8)` (attacker-controlled) and proc.cyr:1130 performs a SECOND arbitrary write at `u_pd + pd_idx*8`. Ring 3 now writes kernel page tables / IDT / GDT at will.
7. The same shadowing also lets segment (b) be aimed at the kernel slab pages (heap.cyr:50 pmm_alloc), so a syscall reading a kmalloc'd fd table or epoll watch list (syscall.cyr:7953-7958 `wl = kpayload(...)`, `load64(wl + wi*16)`) reads attacker bytes and dereferences them.

**Suggested fix.** Reject any PT_LOAD that overlaps the per-process kernel-identity window. The loaders already know the boundary: user segments must stay under the first non-identity PD slot. Either (a) narrow the ceiling to the code/data window actually used by the toolchain (every staged binary bases at 0x400000 with memsz <= 32 MB, so `p_vaddr + p_memsz > 0x2000000` is a safe reject and retires the class the way the 0x400000 floor retired PD[1]), or (b) make proc_map_page/_nx refuse a pd_idx in [3, 127] outright and have the loader map segments through a non-identity window. Independently, move the kernel's identity-VA dereferences off identity: page-table walks in proc_map_page/_nx/_hi/proc_unmap_page/proc_get_user_cr3/sys_munmap and kmalloc pointers should use pmm_kva_for_access(phys) (DIRECTMAP_BASE + phys, PDPT[8+], never overridable by a user segment) — the exact remedy already applied to the PMM bitmap (pmm.cyr:326-330) and to TSS RSP0 (proc.cyr:363).

### ✅ FIXED 1.56.52 — `kernel/core/syscall.cyr:1895` — gpu_shader_op#92: the primitive/vertex arrays validated in pass 1 are re-read from ring-3-writable shm in pass 2 (TOCTOU), and the comment asserting the opposite is false

**Mechanism.** gpu_shader_op_sys copies the 64-byte op RECORDS into the per-CPU kernel buffer (line 4443) — those are genuinely immutable. But for ops 0x0A/0x0B/0x0C the per-primitive geometry lives in an shm SLOT named by the record, and gpo_validate_texlist reads it directly from `pkva = shm_kva[slot]` (syscall.cyr:1940, 1947-2026). gpo_execute -> gpu_tex_list -> gpu_texl_build (gpu.cyr:7567-7654) then re-reads EVERY one of those fields from the same `pkva` and builds the GPU packet from the second read: pw/ph/px/py at gpu.cyr:7583-7588, tid/lid/twh at 7593-7595, and the destination offset `store32(rec + 144, (py * pitch + px * 4))` at 7652. Nothing re-validates them. The shm page stays ring-3-writable the whole time: shm_write#72 (syscall.cyr:8406) permits CROSS-OWNER writes by design — shm_note_xown only increments a counter (line 919-924, 'COUNTED, NEVER REFUSED'). Under smp_sched_aps=1 (smp.cyr:182) a second CPU can rewrite the slot between the two passes. The comment at syscall.cyr:1895-1896 — '⚠ PURE READS on the KERNEL-RESIDENT record and on the slot's kernel VA. Ring 3 cannot change a field between the check and the use.' — is true of the record and false of the slot, and it is the stated reason no re-check exists.

**Failure trace.** Process A on CPU 0 calls syscall(92, desc_uva, 64) with one op 0x0C record naming prim slot id 3 whose 96-byte primitives all carry legal pw/ph/px/py/tw/th. gpo_validate_texlist reads slot 3 and returns 0; gpo_execute_all enters the build loop. Process B (or a second thread of A) on CPU 1 calls syscall(72, id=3, src, 96) and overwrites primitive 0's dwords with px=0xFFFF, py=0xFFFF, twh=(4096<<16)|4096. Neither call takes a lock; both run IF=0 on disjoint CPUs, which serializes nothing. gpu_texl_build then stores dst offset 0xFFFF*pitch + 0xFFFF*4 (~500 MB at pitch 7680) into rec+144 and programs a 4096x4096 texture fetch against a slot the validator sized for a much smaller one. The dispatched shader writes ~500 MB past the back-buffer base into the GPU carveout / VRAM and fetches texels outside the texture slot. gpo_validate_trilist (syscall.cyr:2153) and gpo_validate_tritex (2054) have the same shape for their vertex slots.

**Suggested fix.** Copy the primitive/vertex array out of the shm slot into a per-CPU kernel staging buffer once, validate THAT copy, and have gpu_texl_build/gpu_tri_list read only the copy — the same discipline gpu_shader_op_sys already applies to the 64-byte records via proc_copy_from_user. Then correct the comment at 1895-1896.


## P1 — correctness: wrong results, hangs, races, or a load-bearing false comment — 26 item(s) · 16 FIXED + 1 PARTIAL

### `kernel/arch/aarch64/timer.cyr:12` — aarch64 timer/rdtsc inline asm addresses [sp,#0], which is frame padding, not the intended local

**Mechanism.** The encoded words `0xE0;0x03;0x00;0xF9` = `STR x0,[sp,#0]` and `0xE0;0x03;0x40;0xF9` = `LDR x0,[sp,#0]`. They assume the adjacent Cyrius local lives at sp+0. It does not. Measured against cycc_aarch64 on this toolchain: a function prologue is `stp x29,x30,[sp,#-16]!; mov x29,sp; sub sp,sp,#0x10` with the first local at [x29,#-8] and the frame padded to 16 bytes — so for a 0-param/1-local function sp+0 is the 8-byte PAD at [x29,#-16], and the local is at sp+8. For a 1-param/3-local function the frame is 0x20 with slots at x29-8/-16/-24/-32 and sp+0 = x29-32 = the LAST local. None of the five asm blocks match their intended variable, and none of them documents the register contract the repo requires (x0 is clobbered; the [sp,#0] assumption is unstated).

**Failure trace.** `timer_read_freq()` (line 7): one local `freq` at [x29,#-8]; the STR at line 12 writes CNTFRQ_EL0 into the pad at [x29,#-16]; `return freq` returns the initializer 0. `timer_init` (line 27) therefore always takes the `if (freq == 0) { freq = 62500000; }` fallback and computes the interval from a hardcoded frequency instead of the real CNTFRQ_EL0. `timer_read_count()` (line 17) returns 0 identically, so `serial_print("Timer: freq="...)` in arch/aarch64/main.cyr:11 prints 0. `timer_init`'s first asm (line 33-36) reads sp+0 = the `ctl` slot, which has not been written yet at that point, and programs CNTV_TVAL_EL0 with an uninitialized value. `timer_handler_arm()` (line 48, one local) reloads CNTV_TVAL_EL0 from the pad slot on every tick. The same defect sits in `rdtsc()` at kernel/arch/aarch64/stubs.cyr:240 (`var count = 0;` + STR x0,[sp,#0]) — rdtsc() is a constant 0 on aarch64, which makes `rdrand_u64()` (stubs.cyr:247) a constant 0, i.e. zero KASLR entropy on that arch.

**Suggested fix.** Address the locals through their real frame offsets, or (safer) return the register value directly rather than round-tripping through an assumed stack slot. Whatever form is chosen, add the input/output/clobber comment the repo rule requires — the current comments document only the instruction encoding, not the stack contract that is the part that is wrong.

### ✅ FIXED 1.56.51 — `kernel/arch/x86_64/apic.cyr:281` — tlb_shootdown_all's ack handshake uses two unlocked globals and cannot make progress when two CPUs shoot down at once, silently degrading to the stale TLB it exists to prevent

**Mechanism.** tlb_shoot_ack and tlb_shoot_want (lines 210-211) are plain i64 globals with no lock and no atomicity. tlb_shootdown_all resets ack=0 / want=cpu_count-1 (281-282), IPIs every other CPU (285-288), then spins on `tlb_shoot_ack < tlb_shoot_want` (290-294) with a 2,000,000-iteration bound whose expiry path is documented as 'fail-safe: degrade to stale-TLB risk, never hang' (291). Two problems compound. (1) The sender spins with IF=0 -- every caller is a ring-3 syscall handler, and SFMASK 0x40700 clears IF on SYSCALL entry -- so a spinning sender cannot service the OTHER sender's vector-0xF0 IPI. Two concurrent shootdowns therefore deadlock each other until BOTH time out, and both then proceed with an incomplete flush. (2) tlb_shootdown_handler does `tlb_shoot_ack = tlb_shoot_ack + 1` (line 221), a non-atomic read-modify-write executed by up to three APs simultaneously, so acks are lost even without (1); and a second sender's `tlb_shoot_ack = 0` (281) wipes the first sender's tally mid-flight.

**Failure trace.** Process P is scheduled on CPU1, touches an mmap page at VA V (a 2 MB TLB entry for V is now cached on CPU1), then migrates to CPU0 (sched_next has no affinity). On CPU0, P calls munmap(V) -> sys_munmap (proc.cyr:1836-1846) -> proc_unmap_page -> tlb_shootdown_all (proc.cyr:1693): ack=0, want=3, IPIs to CPUs 1,2,3, spin. At the same moment CPU1 is inside waitpid#4 -> proc_reap_child -> proc_free_address_space -> tlb_shootdown_all (proc.cyr:884), also IF=0, also spinning. Neither CPU can take the other's IPI, so both exhaust TLB_SHOOT_WAIT and return with the flush unperformed. CPU0's sys_munmap then runs `pmm_free_2mb(phys)` at proc.cyr:1845, handing the physical page back to the allocator; pmm_alloc_2mb gives it to process Q. When P is next scheduled on CPU1 and touches V, CPU1's stale 2 MB translation resolves V to the page Q now owns -> P reads and writes Q's memory across the address-space boundary. This is precisely the failure the mechanism was written on 2026-08-03 to eliminate (apic.cyr:189-196).

**Suggested fix.** Serialize the whole handshake under a dedicated fixed-global xchg spinlock (tlb_shootdown_all is a leaf -- it acquires nothing else -- so it fits the smp.cyr lock-order table cleanly), and make the handler's increment atomic (`lock inc [tlb_shoot_ack]`, 0xF0 0x48 0xFF 0x05 or an xadd). The IF=0 mutual-block also needs addressing: either poll for the shootdown vector while spinning (check the LAPIC IRR / call the handler body inline when another shootdown is pending), or use a per-CPU pending-flag array so a spinning sender services incoming requests instead of ignoring them.

### `kernel/arch/x86_64/iommu.cyr:176` — VT-d translation is enabled with root entries and contexts populated for bus 0 only, blocking DMA for every device behind a bridge

**Mechanism.** iommu_init writes exactly one root entry — `store64(iommu_root_table, ctx | 0x01)` at :159, bus 0 — and leaves entries 1..255 as the memset zeros from :151, i.e. not-present. The context loop at :174-177 then calls `iommu_set_context(0, slot, 0)` with a hardcoded bus 0 and func 0, taking only PciDev_slot from pci_devs and ignoring the real bus/func that pci_record stored in the pci_busfunc side array (pci.cyr:431). Because the caller always passes 0, iommu_set_context's own `if (bus != 0) { return 0 - 1; }` guard at :111 can never fire — it is vacuous at its only call site — and a device at 01:00.0 silently gets a context entry written for bus 0's devfn 0 instead. Line 211 then sets GCMD.TE, so translation is enforced against those tables. Neither iommu_wait_status return (:185, :212) is checked, so a failure to actually latch is invisible.

**Failure trace.** Intel VT-d box with an NVMe drive behind a PCIe root port at 01:00.0 (the common layout). pci_scan's 256-bus sweep records it with slot 0, and pci_busfunc holds bus=1. main.cyr:556-557 calls iommu_init after the storage stack is already live. The loop at :174-177 calls iommu_set_context(0, 0, 0), which writes the context entry for bus 0 devfn 0 (the host bridge) — the NVMe's real context, under bus 1's root entry, is never touched, and bus 1's root entry is still the zeroed not-present value from :151. Line 211 sets TE. From the next instant every NVMe DMA — the completion-queue write for any in-flight or subsequent command — is rejected by the IOMMU with no root entry, so ext2 reads and the kybernet exec of /bin/agnsh stall against a command that never completes. The console prints "IOMMU: VT-d enabled, DMA restricted" (main.cyr:558) immediately before the hang.

**Suggested fix.** Take bus and func from pci_busfunc, allocate a context table per bus on demand and set that bus's root entry, and pass the real (bus, slot, func) into iommu_set_context. Until that exists, refuse to set GCMD.TE when any enumerated device sits outside bus 0 func 0, rather than enabling enforcement against tables that do not describe the machine.

### ✅ FIXED 1.56.51 — `kernel/arch/x86_64/mbi.cyr:58` — boot_info is copied and consumed with no magic or struct_size validation, and the copy reads 8 bytes past the 120-byte source

**Mechanism.** boot_info_capture_rdi latches whatever RDI held at kernel entry into boot_info_ptr and then, gated on nothing but `if (src != 0)`, does `memcpy(&boot_info_copy, src, 128)`. Per docs/development/state.md the gnoboot struct is 120 bytes (0x78) and carries magic 0x41474E4F at +0x00 and struct_size at +0x08 — neither is read here, and the fixed 128 is 8 bytes longer than the declared struct (boot_data.cyr's own comment concedes "[16]=128 B covers gnoboot's 120 B ... struct"). Grepping the tree, 0x41474E4F appears in exactly one executable position: main.cyr:429, a diagnostic print. The code says the opposite: proc_set_ring3 (proc.cyr:428-429) stores proc_cs = 0x23 and proc_ss = 0x1B; sel_pair_consistent (sched.cyr:257-261) accepts exactly (0x08,0x10) and (0x23,0x1B); sys_sched_yield (sched.cyr:621-622) writes proc_cs=0x23 / proc_ss=0x1B; and gdt_init puts user DS at selector 0x18 (-> SS 0x1B) and user CS at 0x20 (-> CS 0x23) at gdt.cyr:17-18. Both comments sit directly above the two lines (202 and 206) that load the values into the iretq frame at isr_rsp+128 (CS) and isr_rsp+152 (SS).

**Failure trace.** A reader debugging the torn-selector class -- the #GP(errcode 0x18) at the timer-ISR iretq that cost this repo a documented two-week chase (idt.cyr:244-268, 325-340) -- must decide whether the reported selector 0x18 is a CS or an SS index. The errcode's selector-index form strips the RPL, so 0x18 is ambiguous between GDT[3] (user DS, the SS) and nothing else; the localisation depends entirely on knowing which array holds which. These three comments tell that reader that ring-3 CS is 0x1B, i.e. that the fault is a CS-load rejection, when the hardware is rejecting an SS load of 0x1B from GDT[3] -- the opposite conclusion, and the opposite half of sel_pair_consistent to instrument. The same inversion makes sched_fix_torn_selector and sched_fix_live_frame read as if they repair the wrong field.

**Suggested fix.** sched.cyr:200 -> '(ring-0 0x08 / ring-3 0x23)'; sched.cyr:205 -> '(ring-0 0x10 / ring-3 0x1B)'; proc.cyr:61 -> 'ring-3 (0x23/0x1B)'. Worth stating the derivation once next to sel_pair_consistent -- CS = STAR[63:48]+16 = 0x23, SS = STAR[63:48]+8 = 0x1B, per syscall_msr_init's STAR write -- so the pairing is re-derivable rather than remembered.

### ✅ FIXED 1.56.51 — `kernel/core/syscall.cyr:263` — blit#39's fb_scale_rowbuf is shared across CPUs — its own comment names the SMP arc as the unwind, and the arc shipped without it

**Mechanism.** `var fb_scale_rowbuf[4096]` (32 KB) is module-scope, not per-CPU. The scale>=2 path expands one source row into it (line 8878) and then copies that row to `scale` framebuffer rows (line 8892), with no lock. The handler's own comment at 8864-8866 states: 'The shared rowbuf is safe under the single-core IF=0 syscall invariant (the SMP arc must add this to its unwind list).' The SMP arc is live — smp_wake_enabled=1 (main.cyr:4541), smp_sched_aps=1 (smp.cyr:182), APs pull ready procs — and this buffer was never added to that list. IF=0 is per-CPU and excludes nothing across cores.

**Failure trace.** Compositor process A on CPU 0 calls blit#39 with scale=2 for its window; game process B on CPU 1 calls blit#39 with scale=2 for its own frame. A finishes the expand loop at 8874-8883 (filling fb_scale_rowbuf with A's pixels) and is at the emit loop; B's expand loop overwrites the buffer with B's pixels before A's `while (bl_kr < bl_scale)` block completes. A's second destination row at 8892 is copied from B's data, so B's framebuffer content is painted into A's window rect — a cross-process pixel disclosure through the shared framebuffer, and a corrupted frame for both. Bounds themselves hold (bl_o and bl_c are both capped at 8192 by the gate at 8834), so this is corruption/disclosure rather than an overflow. The same false single-core premise is restated at syscall.cyr:8480-8483, where sysinfo#35's comment claims 'the APs are woken then PARK (IF=0 hlt) — exactly ONE CPU (the BSP) ever schedules'.

**Suggested fix.** Make it per-CPU: `var pcpu_fb_scale_rowbuf[16384]` with a `pcpu_cpu() * 32768` base accessor (4 CPUs x 32 KB), matching pcpu_sc_gpuop at line 1276. Then fix the two stale single-core comments.

### ✅ FIXED 1.56.51 — `kernel/core/syscall.cyr:292` — open#7's sc_open_abs is a single shared path buffer whose 'single-threaded per syscall' justification was invalidated by SMP

**Mechanism.** `var sc_open_abs[32]` is module-scope and NOT per-CPU, and its banner (lines 287-291) ends 'Single-threaded per syscall ⇒ one shared buffer is safe.' Every sibling scratch buffer in this file was converted for SMP and says so — pcpu_ew37_path (line 119, '1.46.x STEP-2 (#3): PER-CPU'), pcpu_spawn_path_buf (145), pcpu_ew37_env (154), pcpu_spawn_env_buf (258), pcpu_redir_backup (178), pcpu_sc_gpuop (1276). sc_open_abs was missed. The #7 handler writes the '/'-prefixed name into it at 7741-7745 and then routes on `op_path = &sc_open_abs` through vfs_resolve_mount (7747) and sys_open_ext2_inner (7756). Both the write and vfs_resolve_mount sit OUTSIDE the fs_spin_lock, which is only taken at 7755. With smp_wake_enabled=1 (main.cyr:4541) and smp_sched_aps=1 (smp.cyr:182), APs pull real ring-3 procs, so two CPUs can be inside this arm concurrently. IF=0 serializes nothing across CPUs.

**Failure trace.** Process A on CPU 0 calls open("config", 6, O_RDONLY): load8(arg1)!=47 so it writes "/config" into sc_open_abs and sets op_len=7. Before it reaches vfs_resolve_mount at 7747, process B on CPU 1 enters the same arm with open("secrets", 7, ...) and overwrites the buffer with "/secrets". CPU 0 then resolves and opens `&sc_open_abs` for 7 bytes — "/secret" — a file it never named. The two processes' fd tables are private, so A ends up holding a handle on B's path (or, with the lengths reversed, a truncated third path). Any privilege reasoning a caller does on the name it passed is void. This is a path-confusion defect reachable by any two concurrent ring-3 processes, and the buffer's own comment is what stops a reader from noticing.

**Suggested fix.** Convert to `var pcpu_sc_open_abs[128]` with an `sc_open_abs_base() { return &pcpu_sc_open_abs + pcpu_cpu() * 256; }` accessor, matching the pcpu_spawn_path_buf pattern at line 145, and rewrite the banner.

### 🟠 PARTIAL 1.56.51 — `kernel/core/syscall.cyr:7415` — The raw-disk-write "capability gate" is a plain magic constant any ring-3 process can send, checked before all validation and never cleared

**Mechanism.** `blk_open_sys(tag, mode)` line 7415 reads `if (mode == BLK_RW_ARM_MAGIC) { blk_rw_armed = 1; return 0; }` as the FIRST statement — before the tag-range check (7416-7417) and before `blk_is_registered` (7418). There is no privilege check of any kind (agnos has no per-proc capabilities; proc.cyr says so). `BLK_RW_ARM_MAGIC = 0x424C4B5F5257` is a compile-time constant sitting in the kernel image. `blk_rw_armed` is a global that is never reset — not on blk_close_sys (7499-7504), not on process exit, not on any error path. So any ring-3 process, including one that has no block handle at all, permanently enables destructive raw-disk writes for the whole system with one syscall. The header comment at 7369-7371 states the shipped band is "the READ-PATH (Phase 1) — enum / open(RO) / read / info / close, all NON-DESTRUCTIVE. blk_write#78 is Phase 2 (capability-gated)" — both halves are false as built: #78 is dispatched at line 8434 and its only gate is this constant.

**Failure trace.** Any ring-3 process: syscall 76 with arg1 = 0 (not even a valid tag) and arg2 = 0x424C4B5F5257. Line 7415 fires, blk_rw_armed = 1, returns 0. From that point on syscall 78 (line 8434 → blk_write_sys, whose only gate is `if (blk_rw_armed == 0)` at 7461) will write attacker data to any LBA of any registered device — and, per the two findings above, with an unbounded LBA on secondary backends. A shell script or any spawned binary can wipe the GPT and the root filesystem.

**Suggested fix.** Move the arm branch below the tag/registration validation, and replace the constant with a real check — at minimum gate it on a privileged pid/first-process check until per-proc capabilities land; clear `blk_rw_armed` on process exit and on blk_close. Also correct the 7369-7371 header comment so it no longer claims the band is non-destructive.
