All 7 converted; every sweep gate is now guarded. `QEMU_TRIES` 3 → **6**: the header's "roughly 1 boot in 4" is optimistic — measured **3 banners in 10 attempts** on this host. ⚠ **Before calling any sweep red a regression, check the gate's log for `AGNOS kernel v`.** A missing banner means the run measured NOTHING.
- ⭐⭐ **`fp-nm-smoke` IS NOT A COIN FLIP AND NEVER WAS AN FP DEFECT — this entry was WRONG, corrected 2026-08-30.** It previously read "~50% COIN FLIP … 2 of 4 runs FAIL on the RELEASED 1.56.51, same build, same host" and told future sessions not to bisect against it. The real cause: `fp-nm-smoke` was one of **7 sweep gates using the UNGUARDED `qemu_dwell`** instead of `qemu_dwell_kernel`, so an OVMF hand-off failure — the kernel never executing — was reported as failed FP assertions. Its own recorded failure shape ("`fp: #NM serviced` absent + `boot did not reach shell`") is exactly what an EMPTY log produces. ⇒ Measured with the guard in place: **6 runs, 6 passes**, two needing a retry and both of which would have been reds before. ⚠ Not a claim it can never fail: a run exhausting all `QEMU_TRIES` still scores red, but it now SAYS so (`treat this run as VOID, not as a failure`) instead of naming an FP property. ⛔ **The general lesson is the one worth keeping: a gate that reports a property it never measured will be recorded as a flaky PROPERTY, and the note will then discourage anyone from looking.** This entry did that for ~2 days.
- ⚠ **`ktest.sh`'s in-kernel suite has 6 real failures** (pmm x2, vfs empty-pipe x1, initrd x3) — PRE-EXISTING, measured identical on a clean tree, and visible for the first time only because the harness now boots at all (its ESP was 64 MB, outside the one measured-working cell). Unexplained.
- ⚠ **`ring3-smoke` has 4 real failures** (preempt gate, parent spawn+wait, stress, yield) — PRE-EXISTING, measured identical against `ffdb611`, visible only once the virtio-blk conversion made the smoke runnable. Genuine ring-3 spawn/yield defects, unexplained.
- **`modeset-tool-smoke` mask** — `MDO_OP_SUPPORTED` is **`0xE7F` = 3711** (un-armed) / **`0xFFF` = 4095** (armed); bit 11 = `MDO_OP_NATIVE`, in BOTH values because it carries no audio content and must exist in a plain kernel. The smoke asserts both directions.

- ⛔⛔ **"PRE-EXISTING" AND "UNEXPLAINED" ARE NOT DIAGNOSES — they are what a red gate gets called when nobody re-derives it.** Six ktest failures carried that label; **two were gates asserting contracts this tree had itself changed** (an empty pipe returning -2 since *ipc bites 10/11*; a 4096-page bitmap that is 65536), and three more are environmental (no initramfs is loaded, so the `[initrd]` tests cannot pass here). Only the label was pre-existing. ⇒ When a gate has been red long enough to be described rather than fixed, re-derive what it asserts against the code **before** carrying the number forward. ⭐ And where a bound can be derived, derive it: the PMM one now reads `pmm_bitmap_pages` instead of a literal, so it follows the allocator rather than going stale a second time.
- ⛔⛔ **CYRIUS IS NEVER-TOUCH. A CROSS-REPO ASK IS FILED IN `cyrius/docs/development/issues/YYYY-MM-DD-item.md`, NOT HERE AND NOT AS A CODE EDIT.** (Operator ruling, 2026-08-30.) agnos mints syscall numbers; cyrius owns the `lib/syscalls_x86_64_agnos.cyr` peer, and the way to ask for one is an issue **in cyrius's own issues folder** where its maintainer works — not an agnos-side issue nobody upstream reads, which is exactly how a samay stdlib finding sat unfiled for six weeks. ⚠ **The consequence is a KNOWN RED GATE, and that is acceptable**: `check.sh`'s *syscall ABI (kernel/doc/cyrius agree)* reads `kernel N · abi-doc N · cyrius N-1` until the peer lands. `symlink`#63 and `readlink`#70 both shipped in exactly this state and both peers have since landed. ⇒ Do NOT "fix" that gate by editing cyrius, and do NOT weaken the gate. Ring 3 can call a peerless syscall by raw number meanwhile.
- ⭐ **AN IRON BURN IS A DEFECT SOURCE, NOT JUST A PASS/FAIL — read the whole capture.** `#tracker-iron-v1` returned green on every marker the tracker named, and the *unasked-for* part of the log carried a real finding: `kriya ls: cannot access '/sl_s': operation not permitted`, five times, from two entries that could be listed but neither stat'd nor removed. That produced `lstat`#102, a syscall whose roadmap row had been blocked on "a consumer" for months. ⚠ It also carried a FALSE lead that a hexdump killed in one command: garbled command lines were `08 20 08` backspace-space-backspace erase sequences, i.e. the operator correcting typos, not HID corruption. Check the bytes before believing a pattern.
- ⛔⛔ **REVIEW THE FIX, NOT JUST THE FINDING — an adversarial pass over this cut's own P2 batch found 15 real defects, ALL OF THEM IN THE FIXES.** Every one had already survived build + check.sh + fmt + a targeted smoke. The shapes recur and are worth knowing: **(a) a gate placed before the thing it inspects** (`tss_ist_selftest`'s vector-32 arm read the IDT twelve lines before the timer gate was installed, so it passed unconditionally); **(b) a helper that does not do what its name says under the caller's conditions** (`acpi_va` only translates under CR3 0x1000, and the caller runs on a proc CR3 — the fix returned exactly the address it was called to translate); **(c) the fix reopening its own hole one address over** (admitting 127/8 "for loopback" let a WIRE frame with dst 127.0.0.1 take the ICMP reply path); **(d) the sibling site left alone** (ICMP and UDP got the destination gate, TCP did not — and TCP was the worse case); **(e) the error path undoing the fix** (`msc_reset_recovery` re-established the exact Link-TRB polarity `msc_alloc_bulk_ring` had just been fixed to remove). ⇒ **Budget review effort for the FIX at least equal to the finding.** A fix is new code written under the confidence of having understood the bug, which is precisely when the surrounding conditions go unchecked.
- ⭐ **A BACKLOG TABLE WITHOUT INLINE MARKERS ROTS SILENTLY — the P2 section said `0 FIXED` while 14 of its 29 items were already done.** The P0/P1 sections carry inline ✅ markers and stayed honest; this one had only a header count, and it disagreed with the code for two days. ⭐ Re-derived by READING EACH SITE (not the git log — the fixes were in the uncommitted working tree), with **every already-fixed claim adversarially refuted before being recorded**, because a false ✅ buries a live defect where nobody looks again. ⇒ When a status count and an item list can disagree, they will. Mark items, not totals.
- ⛔⛔ **`var x[N]` SIZING IS THE HIGHEST-YIELD TRAP IN THIS TREE — VERIFY IT, NEVER RECALL IT.** Function-local is **N BYTES**; module-scope is *usually* N u64 = 8N but is **NOT uniform** (main.cyr records `var fpctxsw_payload[24]` measuring 24 B beside `var fpu_state[1026]` measuring 8208 B). Measured under the 6.5.36 pin: writing 512 B into a fn-local `var a[64]` SIGSEGVs; 64 and 65 do not. ⛔ This one trap has now produced BOTH failure directions in this audit: a cluster of PHANTOM overflow findings (an auditor reading module `var x[N]` as N bytes), and four REAL ring-0 stack overflows in `shell.cyr` that 1.56.51 looked straight at and could not see, because its own comment asserted the wrong rule for the very buffer it was fixing. Verify by `&next-&this` or by an over-write probe.
- ⛔ **THE 1.56.51 SEVERITY LABELS ARE NOT RELIABLE IN EITHER DIRECTION — a second pass found a P0 in the P2 list.** `proc.cyr:1830` (filed P2) is a P0: `sys_munmap`'s signed wrap reached `pmm_free_2mb` on live kernel identity pages from two ring-3 integers. `elf.cyr:357` / `proc.cyr:1788` (filed P2) are ring-3 memory exhaustion. Conversely `elf.cyr:484` was filed as a memory-safety overrun and only spills into the child's own stack page. ⚠ Two of the audit's own suggested fixes are WRONG: the `blk` arm reorder breaks the ABI (measured, reverted), and its init-stack guard is off by one. Re-read against the code.
- ⭐ **usb-storage IS reachable in QEMU — the MSC driver simply had no harness.** `-device usb-storage,bus=xhci.0` enumerates and registers on the first boot that tries it; the catch is that OVMF then offers the stick as a boot option and stops at its menu, so the NVMe drive needs `bootindex=0`. Before 1.56.52 the whole ~1500-line transport had ZERO coverage. `scripts/smoke/msc-short-smoke.sh` is the first, and it is an A/B (injected must refuse, plain must succeed).
- ⚠ **Three 1.56.52 fixes are ASSERTED, NOT EXERCISED.** (a) TSS I/O-map base — `tss_iopb_selftest` proves the value lands in the field the CPU reads (0x66) and the reserved u16 stays clear, but runs no ring-3 `IN`/`OUT`. (b) `syscall_hw.cyr`'s IBRS relocation — emit-order only; its A/B returned a null (3 runs/arm, both boot) and why the old position does not fault under TCG is UNEXPLAINED. (c) `#92` op 0x0C is iron-only (`gpu_present == 0` under QEMU), so the 171-case battery proves the refusal logic, not the hardware path.
- ⚠ **`#92` op 0x0C is still NOT SMP-safe.** The snapshot closes validate-vs-use only; `GPU_TEXL_PREP_SUBOFF` is one shared 512-record prep slot and `gpu_texl_maxw/maxh/colmajor` are global latches, so two CPUs still stomp each other's build. Pre-existing, wrong-picture class, NOT re-opened by the fix.
- ⛔ **Kernel structures are addressed through the DIRECT MAP now** (`pmm_kva_for_access` = `DIRECTMAP_BASE + phys`): all page-table walks, `kmalloc`, the MSC row table. New code that dereferences a `pmm_alloc` result by its raw physical value re-opens a ring-3 → arbitrary-kernel-write class. PDE *values* stay raw phys.
